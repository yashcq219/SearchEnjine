# IndexLoader Implementation Plan

---

# Section 1 — Public API

## Overview

The **IndexLoader** is the first component executed when the Search Engine starts. Its primary responsibility is to read the database generated by the Indexer and construct an efficient in-memory inverted index that will be used by the RankingEngine for all search requests.

Unlike the Indexer, which continuously processes and stores data, the IndexLoader only performs a one-time initialization. Once the loading process is complete, it remains idle while the remaining components use the generated HashMap for searching.

The IndexLoader is intentionally designed as a separate component to isolate all storage-related operations from the searching logic. This separation improves maintainability and allows future database format changes without affecting the RankingEngine or REST APIs.

---

## Responsibilities

The IndexLoader performs the following operations:

- Open the database generated by the Indexer.
- Read every indexed word sequentially.
- Read the posting list associated with each word.
- Select the **Top 10 URLs** having the highest occurrence frequency.
- Construct an in-memory HashMap.
- Validate loaded records.
- Expose the completed HashMap to the RankingEngine.

---

## Public API Methods

| Function Name | Parameter(s) | Return Type | Purpose |
| :--- | :--- | :--- | :--- |
| `IndexLoader` | *None* | N/A (Constructor) | Constructs an `IndexLoader` instance and initializes `m_isLoaded = false` and `m_maxUrlsPerWord = 10`. |
| `~IndexLoader` | *None* | N/A (Destructor) | Destroys the `IndexLoader` instance and automatically calls `clear()` to free allocated memory. |
| `loadFromDatabase` | `const std::string& dbPath` | `bool` | Opens SQLite database at `dbPath`, reads word postings, deduplicates/sorts top 10 URLs per word, and builds the in-memory inverted index map. Returns `true` on success. |
| `hasWord` | `const std::string& word` | `bool` | Performs an O(1) lookup check to verify if a word exists in the loaded inverted index. |
| `getPostings` | `const std::string& word`, `DynamicArray<Posting>& outPostings` | `bool` | Fetches the Top 10 posting list for `word` into `outPostings`. Returns `true` if found, `false` otherwise. |
| `getIndex` | *None* | `const HashMap<std::string, DynamicArray<Posting>>&` | Returns a const reference to the complete in-memory inverted index map. |
| `getLoadedWordCount` | *None* | `int` | Returns the total count of unique searchable words loaded in memory. |
| `isLoaded` | *None* | `bool` | Returns `true` if database loading has completed successfully, `false` otherwise. |
| `getMaxUrlsPerWord` | *None* | `int` | Returns the maximum number of URLs retained per word (default: 10). |
| `clear` | *None* | `void` | Resets the in-memory inverted index map, frees memory, and sets `m_isLoaded` flag to `false`. |

The component produces an in-memory HashMap.

↓

```

## Design Decisions

### Decision 1 — Separate Loading from Searching

The IndexLoader only performs initialization.

Searching is handled entirely by the RankingEngine.

This separation follows the **Single Responsibility Principle**, making each component easier to develop, test, and maintain.

---

### Decision 2 — Load Everything During Startup

Instead of accessing the database for every search query, all searchable data is loaded once during server startup.

Advantages:

- Eliminates repeated disk access.
- Produces predictable query response time.
- Reduces server latency.
- Simplifies request processing.

Since the database is static after indexing, loading it once is sufficient.

---

### Decision 3 — HashMap as Primary Storage

The search engine always performs searches by words.

For example,

```
machine learning search
```

requires finding

```
machine

learning

search
```

independently.

HashMap provides average **O(1)** lookup complexity, making it the most suitable data structure for mapping words to posting lists.

---

### Decision 4 — DynamicArray for Posting Lists

Each indexed word corresponds to multiple documents.

A DynamicArray is selected because:

- posting lists become read-only after loading,
- searching requires sequential traversal,
- contiguous memory improves cache locality,
- lower memory overhead than linked lists.

The component never performs insertion after initialization.

Therefore, DynamicArray provides the best trade-off between memory usage and traversal speed.

---

### Decision 5 — Store Only Top 10 URLs in descending order acc. to occurrence frequency

Some words may appear in thousands of documents.

Loading every posting into memory would:

- increase memory usage,
- increase traversal time,
- increase ranking cost.

Instead, only the **ten URLs having the highest occurrence frequency** are retained.

Advantages:
- decreasing order of occurence frequency decreases the ranking cost
- Smaller memory footprint.
- Faster ranking.
- Lower traversal cost.
- Faster query response.

Trade-off:

Some lower-ranked documents may be ignored during complex multi-word searches. This optimization intentionally prioritizes search speed over complete recall for this educational implementation.

Keeping only the ten highest-frequency URLs significantly reduces memory usage.

Example

```

↓

```

```

This reduces:

- RAM consumption
- Ranking time
- Search latency

without changing the public interface of the component.

# Section 3 — Failure Handling

| Failure | Handling Strategy |
|----------|-------------------|
| Database file missing | Abort initialization and report failure. |
| Database cannot be opened | Stop server startup. |
| Corrupted record | Skip invalid record and continue loading. |
| Empty word | Ignore the record. |
| Empty posting list | Ignore the word. |
| Invalid URL identifier | Skip invalid posting. |
| Negative occurrence | Ignore posting. |
| Duplicate words | Merge duplicate posting lists before selecting the top 10 URLs. |
| Memory allocation failure | Abort loading and report initialization failure. |

The IndexLoader attempts to recover from recoverable errors while ensuring the resulting HashMap remains valid.

# Section 4 — Complexity Analysis

## Variables
- **N** = Number of unique indexed words stored in memory.
- **P** = Total raw posting rows stored in the SQLite database.
- **K** = Number of raw postings associated with a specific word in the database.
- **M** = Maximum URLs retained per word ($M = 10$ by default).

## Public Methods Time Complexity Table

| Public Method | Best Case | Average Case | Worst Case | Reason / Explanation |
| :--- | :--- | :--- | :--- | :--- |
| `IndexLoader()` | $O(1)$ | $O(1)$ | $O(1)$ | Initializes primitive member flags (`m_isLoaded = false`, `m_maxUrlsPerWord = 10`) in constant time. |
| `~IndexLoader()` | $O(N \cdot M)$ | $O(N \cdot M)$ | $O(N \cdot M)$ | Automatically calls `clear()`, which iterates over all $N$ buckets in `m_index` to free allocated nodes. |
| `loadFromDatabase(dbPath)` | $O(P + N \cdot K^2)$ | $O(P + N \cdot K^2)$ | $O(P + N \cdot K^2)$ | Reads $P$ SQLite rows ($O(P)$), deduplicates $K$ postings per word ($O(K)$), and applies insertion sort ($O(K^2)$) to select top $M$ URLs for each of the $N$ words. |
| `hasWord(word)` | $O(1)$ | $O(1)$ | $O(N)$ | Computes string hash and checks bucket in `m_index`. Takes $O(1)$ average time, worst-case $O(N)$ if all words hash to the same bucket. |
| `getPostings(word, out)` | $O(1)$ | $O(1)$ | $O(N + M)$ | Performs $O(1)$ average hash map lookup for `word`, then copies at most $M = 10$ postings into the output array ($O(M) = O(1)$). |
| `getIndex()` | $O(1)$ | $O(1)$ | $O(1)$ | Returns a direct `const` reference to `m_index` without any data copying or traversal. |
| `getLoadedWordCount()` | $O(1)$ | $O(1)$ | $O(1)$ | Directly returns the pre-calculated integer size field stored in `m_index.getSize()`. |
| `isLoaded()` | $O(1)$ | $O(1)$ | $O(1)$ | Reads and returns the boolean flag `m_isLoaded` in constant time. |
| `getMaxUrlsPerWord()` | $O(1)$ | $O(1)$ | $O(1)$ | Reads and returns the integer constant `m_maxUrlsPerWord` (10) in constant time. |
| `clear()` | $O(N \cdot M)$ | $O(N \cdot M)$ | $O(N \cdot M)$ | Iterates through all $N$ buckets in `m_index` and frees all dynamically allocated chain nodes. |

> [!NOTE]
> Because only $M = 10$ URLs are retained per word, memory consumption remains strictly bounded ($O(N \cdot M)$) regardless of total postings stored on disk.

# Section 5 — Future Compatibility

The IndexLoader is designed to isolate all database access from the remaining Search Engine components.

The RankingEngine communicates only with the HashMap produced by the IndexLoader. Consequently, any future modifications to the database format require changes only inside the IndexLoader, leaving the remaining architecture unaffected.

The current implementation stores only the top ten URLs for every indexed word. This limit is intentionally configurable and can be modified in future versions without affecting other components.

Possible future improvements include:

- Loading complete posting lists instead of the top ten URLs.
- Supporting compressed posting lists.
- Loading positional indexes for phrase searching.
- Loading document metadata such as title, page rank, or document length.
- Incremental index updates without restarting the server.
- Lazy loading of infrequently searched words.
- Memory-mapped index files for handling very large datasets.

Because the IndexLoader exposes a consistent in-memory HashMap, these enhancements can be implemented internally while preserving compatibility with the RankingEngine and REST API Layer.

The component therefore serves as a stable abstraction between persistent storage and the in-memory search infrastructure, ensuring that future optimizations remain localized to a single component without requiring changes to the rest of the Search Engine.
