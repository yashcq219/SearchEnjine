# Search Engine Implementation Plan

# Introduction

## Project Overview

The **Search Engine** is the final component of the Information Retrieval System developed after the completion of the **Crawler** and **Indexer** projects. While the Crawler is responsible for collecting web pages and the Indexer extracts searchable words to construct an inverted index, the Search Engine enables users to efficiently retrieve relevant documents through a web-based interface.

The frontend of the system is developed using **HTML**, **CSS**, and **JavaScript**, providing a lightweight and responsive user interface. The backend is implemented in **C++** using the **Crow Web Framework**, exposing RESTful APIs that process search queries and return ranked search results in JSON format.

Unlike the previous projects, the Search Engine does not crawl websites or generate indexes. Instead, it consumes the database generated by the Indexer, loads the searchable data into memory during server initialization, processes incoming search queries, ranks the most relevant pages, and returns the best matching URLs to the frontend.

The system follows a modular architecture in which every component is responsible for a single task. This separation of concerns improves maintainability, simplifies testing, and provides a scalable foundation for future enhancements such as TF-IDF ranking, BM25, phrase searching, autocomplete, and query caching.

---

# Project Objectives

The primary objectives of the Search Engine are:

- Develop a RESTful Search Engine backend using modern C++.
- Load the inverted index generated by the Indexer into memory.
- Process user search queries efficiently.
- Rank search results according to their relevance.
- Return lightweight JSON responses to the frontend.
- Build a modular architecture that supports future scalability and enhancements.

---

# System Components

The Search Engine consists of four primary components.

## 1. IndexLoader

The **IndexLoader** is executed once during server startup. It reads the database generated by the Indexer, extracts the indexed words and their corresponding posting lists, selects the highest-frequency URLs for each word, and constructs the in-memory HashMap used throughout the searching process.

Since all searchable data is loaded into memory during initialization, no database access is required while processing user queries.

---

## 2. Tokenizer

The **Tokenizer** is reused directly from the Indexer project through a Git submodule.

It performs:

- Lowercase normalization
- Punctuation removal
- Stop-word removal

The processed query words are returned as a DynamicArray and forwarded to the RankingEngine.

Using the same Tokenizer for both indexing and searching guarantees identical preprocessing rules, ensuring consistency between indexed terms and user queries.

---

## 3. RankingEngine

The **RankingEngine** is the core component of the Search Engine.

It receives the processed query words, retrieves the corresponding posting lists from the HashMap, evaluates document relevance, and ranks pages according to the following strategy:

1. Pages containing **all query words** (AND Matching)
2. Pages containing **one or more query words** (Partial Matching)
3. Ranking based on total occurrence frequency

Finally, the RankingEngine returns a maximum of **10** recommended URLs.

---

## 4. REST API Layer

The **REST API Layer** provides communication between the frontend and the Search Engine backend.

Implemented using the **Crow Web Framework**, it exposes REST endpoints including:

- `/search`
- `/health`

The REST API validates incoming requests, invokes the RankingEngine, converts the returned results into JSON format, and sends the response back to the frontend.

# Design Philosophy

The Search Engine follows a **layered and modular architecture**, where every component has a single, clearly defined responsibility.

- **IndexLoader** is responsible for loading and organizing indexed data.
- **Tokenizer** preprocesses user queries using the same logic employed during indexing.
- **RankingEngine** performs query evaluation, relevance calculation, and document ranking.
- **REST API Layer** manages communication between the frontend and backend.

This separation minimizes coupling between components, improves maintainability, and enables future enhancements—including TF-IDF, BM25, phrase searching, autocomplete, query caching, and distributed search—without requiring significant architectural changes.
