# RankingEngine Implementation Plan

---

# Section 1 — Public API

## Overview

The RankingEngine is the core component of the Search Engine. It receives the tokenized query from the Tokenizer, retrieves the corresponding posting lists from the in-memory HashMap generated by the IndexLoader, evaluates the relevance of each document, and returns the most relevant search results.

Unlike the IndexLoader, which prepares data during server startup, the RankingEngine executes once for every search request.

Its primary objective is to identify documents matching the user's query and rank them according to their relevance.

---

## Responsibilities

The RankingEngine performs the following operations:

- Receive the tokenized query.
- Retrieve posting lists for every query word.
- Perform HashMap lookups.
- Identify pages containing all query words.
- Identify pages containing one or more query words.
- Rank pages according to occurrence frequency and number of matched words.
- Return at most ten recommended URLs.

## Design Decisions

### Decision 1 — HashMap Lookup

Each query word is searched independently inside the HashMap.

Example

```
machine

↓

Posting List
```

```
learning

↓

Posting List
```

HashMap lookup provides average O(1) access time, allowing every query word to be located efficiently.

---

### Decision 2 — Two-Phase Ranking

The RankingEngine ranks pages in two stages.

#### Phase 1 — Exact Match

Pages containing **every query word** are selected first.

Example

Query

```
machine learning
```

Result

```
Page A

machine ✔

learning ✔
```

These pages are considered the most relevant because they satisfy the complete search query.

---

#### Phase 2 — Partial Match

If fewer than ten pages satisfy the complete query, the remaining slots are filled using pages that contain one or more query words.

Example

```
Page B

machine ✔

learning ✘
```

```
Page C

machine ✘

learning ✔
```

These pages are ranked after all exact matches.

---

### Decision 3 — Ranking by Occurrence Frequency

If multiple pages satisfy the same matching condition, they are ranked according to the total occurrence frequency of the matched words.

Example

Query

```
cpp crow
```

Page A

```
cpp = 8

crow = 7

Score = 15
```

Page B

```
cpp = 4

crow = 3

Score = 7
```

Page A receives a higher ranking because the search terms appear more frequently.

---

### Decision 4 — Maximum of Ten Results

The RankingEngine returns at most ten URLs.

Reason

- Reduces response size.
- Decreases JSON serialization time.
- Matches the number of results displayed by the frontend.
- Prevents unnecessary ranking of low-relevance pages.

---

### Decision 5 — Ranking Independent of REST API

The RankingEngine is responsible only for determining the most relevant pages.

It has no knowledge of:

- HTTP requests
- JSON responses
- Crow

This separation keeps the searching logic independent from communication logic.

# Section 3 — Failure Handling

| Failure | Handling Strategy |
|----------|-------------------|
| Empty token list | Return an empty result list. |
| Query word not found | Ignore the missing word and continue processing remaining words. |
| No exact match | Execute partial matching phase. |
| No matching pages | Return an empty URL list. |
| Duplicate URLs in posting lists | Merge scores before ranking. |
| More than ten results | Return only the highest-ranked ten URLs. |

The RankingEngine always attempts to return the best available results rather than terminating due to missing words.

# Section 4 — Complexity Analysis

Assume:

- **W** = Number of query words.
- **K** = Maximum posting list size (10).
- **R** = Number of candidate pages.

| Operation | Best | Average | Worst |
|------------|------|----------|--------|
| HashMap lookup | O(1) | O(1) | O(n) |
| Read posting list | O(K) | O(K) | O(K) |
| Compare candidate pages | O(R) | O(R) | O(R) |
| Frequency scoring | O(R) | O(R) | O(R) |
| Sort ranked pages | O(R log R) | O(R log R) | O(R²)* |
| Return Top 10 URLs | O(10) | O(10) | O(10) |

Where:

- **W** = Number of query words.
- **K** = Maximum posting list size (10).
- **R** = Number of candidate pages after merging posting lists.

> *Worst-case sorting assumes QuickSort with poor pivot selection.*

# Section 5 — Future Compatibility

The RankingEngine is designed independently of both the Tokenizer and the REST API.

It receives only:

- tokenized query words,
- the HashMap generated by the IndexLoader.

Because of this separation, future improvements to the ranking algorithm can be implemented without modifying the remaining components.

Possible future enhancements include:

- LFU Cache.
- TF-IDF ranking(Term Frequency - Inverse Document Frequency).
- BM25 ranking.
- Phrase matching.
- Proximity search.
- Title boosting.
- Page popularity ranking.
- Freshness-based ranking.
- Personalized ranking.
- Synonym-aware searching.

The current implementation ranks pages using:

1. Complete query matches.
2. Partial query matches.
3. Total occurrence frequency.

This provides a simple and efficient ranking strategy while maintaining a modular architecture that can support more advanced search algorithms in future versions.
